# filter-check · 列表筛选检查 Skill

## 它检查什么（一句话）

**检查任意列表组件的筛选是不是「三态齐全、无结果时不是死胡同、无障碍达标」，并保证不打断其他视图。**

## 何时用它

- 新增一个列表组件（或给已有组件加筛选）
- 改动筛选器、关键词输入、列表渲染逻辑之后
- 筛选相关改动提交之前

## 检查清单（必须逐条给出结论，不得跳过）

### A. 三种情况（每个组件必查）

| 编号 | 情况 | 判定标准 |
|---|---|---|
| A1 | 有结果 | 输入一个数据里存在的条件 → 条数正确，且**每条内容确实匹配**（不是只改了计数） |
| A2 | 无结果 | 输入一个不存在的内容 → **列表零条目** + 显示文案 + **有出口按钮**（三者缺一即 FAIL） |
| A3 | 清空恢复 | 点出口按钮 / 手动清空输入框 → 条数恢复为**该条件下**的完整列表，计数文案同步回到基线 |

### B. 空数据态与其它边界

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| B1 | 零数据 ≠ 筛空 | 组件**本身没有数据**时（如一条都没收藏）与「筛了但没匹配」**文案必须不同**——前者引导去获取数据，后者提示换条件 |
| B2 | 输入即过滤 | 输入过程中实时过滤，不需要再点「搜索」按钮 |
| B3 | 多条件叠加 | 组件同时有条件筛选 + 关键词时，两者叠加生效，且计数能同时反映 |

### C. 交互与无障碍

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| C1 | 计数反馈 | 计数文案随筛选实时更新；容器带 `aria-live="polite"`（读屏可播报） |
| C2 | 选中态唯一 | 条件筛选同一时刻只有一个 `.active` |
| C3 | 键盘可操作 | 聚焦后按 Enter 能触发筛选（原生 button 天然满足） |
| C4 | 无障碍状态 | 选中项 `aria-pressed="true"`、其余 `"false"`；容器 `role="group"` + `aria-label` |
| C5 | 触控尺寸 | 筛选项高度 ≥ 44px |
| C6 | 窄屏 | 375px 视口横向溢出 = 0px |

### D. 回归底线

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| D1 | 其他视图不受影响 | 其余视图/组件仍能正常渲染（有条目或正确空态，无报错） |
| D2 | 无 JS 错误 | 全流程 `pageerror` 数量为 0 |

## 执行方式

```bash
# 项目根目录先起服务器
python -m http.server 8000 --bind 127.0.0.1

# 另开终端：全部已登记组件都查（board / search / forum / favs + source 单独指定）
node .workbuddy/skills/filter-check/filter-check.js

# 只查某一个组件
node .workbuddy/skills/filter-check/filter-check.js favs
```

脚本对每个组件逐项断言并打印 JSON；出现 `FAIL:` 行即不通过，退出码 1。

## 输出与留痕

- 每次调用把结果追加到本目录 `run-log.md`：日期、目标组件、各项结论、总体结果。
- 发现不通过项：**先修代码再重跑**，不允许「记录问题但带着问题提交」。

## 已知边界

- 只覆盖「本地静态筛选与站内检索」（`search` 组件即是站内检索的 L1 部分），不覆盖后端检索（L3 自动联网 + AI 整合，待接后端）。
- **用例取值不依赖数据分布**：基线条数、某结论的条数、某关键词的条数一律从 `data/data.json` /
  `data/posts.json` 现算（Day 16 起）；只有「挑哪个关键词当用例」是写死的，且带守卫——
  数据里查不到就直接报错退出，不会让「0 条 == 0 条」静默通过。
- `board` 与 `favs` 现在都有计数元素（`#filter-summary` / `#fav-summary`）与关键词框，
  内核里的对应断言一律照常执行，没有豁免项。
