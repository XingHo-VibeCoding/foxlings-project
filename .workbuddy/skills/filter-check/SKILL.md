# filter-check · 筛选交互检查 Skill

## 它检查什么（一句话）

**检查筛选交互的三种情况（有结果 / 无结果 / 清空恢复）是否都正确，外加可访问性底线。**

## 何时用它

- 改动首页结论筛选器（`index.html` 的 `#verdict-filter`）
- 改动卡片流渲染逻辑（`js/home.js` 的 `renderFilteredFeed` / `applyFilter`）
- 每次筛选相关改动提交之前

## 前置条件

1. 本地服务器在跑：项目根目录执行
   `python -m http.server 8000 --bind 127.0.0.1`
2. 有 playwright-core 可用的 node 环境（绝对路径见项目 RUN.md 所在机器的既有配置）

## 检查清单（必须逐条给出结论，不得跳过）

### A. 三种情况

| 编号 | 情况 | 判定标准 |
|---|---|---|
| A1 | 有结果 | 选一个数据里存在的结论（当前 demo 数据：假=1、存疑=4）→ 卡片数 = 该结论条目数，且每张卡片的结论标签都等于所选值 |
| A2 | 无结果 | 选一个数据里不存在的结论（当前 demo 数据：真=0）→ 显示空状态文案（含所筛结论名）+「显示全部」按钮，且**不出现任何卡片** |
| A3 | 清空恢复 | 点「显示全部」（或顶部「全部」chip）→ 卡片数恢复为全量条数，计数文案回到「共 N 条」 |

### B. 交互与无障碍（加练项，一并检查）

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| B1 | 计数反馈 | 结果计数文案随筛选实时更新（`#filter-summary`），非「全部」时含所筛结论名 |
| B2 | 选中态 | 只有被选中的 chip 带 `.active`，其余不带 |
| B3 | 键盘可操作 | 聚焦 chip 后按 Enter 能触发筛选（原生 button 应天然满足） |
| B4 | 无障碍状态 | 选中 chip `aria-pressed="true"`，其余 `"false"`；筛选器容器有 `role="group"` + `aria-label` |
| B5 | 触控尺寸 | chip 高度 ≥ 44px |
| B6 | 窄屏 | 375px 视口下横向溢出 = 0px |

### C. 回归底线

| 编号 | 检查项 | 判定标准 |
|---|---|---|
| C1 | 榜单不受影响 | 辟谣榜视图仍能渲染（切入榜单有条目或空状态提示，无报错） |
| C2 | 无 JS 错误 | 全流程 `pageerror` 数量为 0 |

## 执行方式

```bash
node <本机既有路径>/filter-check.js
```

脚本对 A/B/C 三组逐项断言并打印 JSON 结果；出现 `FAIL:` 行即不通过。

## 输出与留痕

- 每次调用必须把结果追加到本目录的 `run-log.md`：日期、执行项、各项结论、总体结果。
- 发现不通过项：先修代码再重跑，不允许「记录问题但带着问题提交」。

## 已知边界

- 只覆盖结论筛选，不覆盖辟谣榜的时间档筛选与关键词检索（那是 board 的既有逻辑，另行检查）。
- 依赖 demo 数据分布（假=1、存疑=4、真=0）；数据换了之后 A1/A2 的用例取值要跟着换。
