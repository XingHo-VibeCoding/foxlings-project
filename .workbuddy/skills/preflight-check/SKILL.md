# preflight-check · 发布前检查 Skill

## 它检查什么（一句话）

**在按下「发布」之前，用一条命令回答「现在这一版能不能发」——红线项必须全绿，其余项如实报出来。**

## 何时用它

- 要发布 / 重新发布这个站之前
- 改动之后准备上线之前（本地门槛管「工艺」，这一条管「能不能出门」）
- 每天收尾当健康体检（顺手看一眼线上是不是还是最新版）

## 何时不用

- 只是本地改代码、还没打算发 —— 用 frontend-rules / filter-check 那两条工艺门槛就够
- 只改文档、不碰仓库的可发布内容

## 它只做两件事

| # | 做什么 | 为什么这么做 |
|---|---|---|
| ① | **把已有门槛串成一条流水** | `check-secrets.js` 是密钥口径的唯一真值来源，`check-boundaries.js` 是边界口径的。本 Skill 只**调用**它们、只**读**它们导出的规则表，绝不抄第二份 —— 两份定义各自演化的那天，就会出现「一个脚本说 0 条、另一个说有 3 条」的糊涂账 |
| ② | **补上现有门槛没覆盖的四类检查** | 公网可达 / `.env` 忽略是否**真生效** / 工作区与远端是否就绪 / 线上是不是最新版。这些不属于「工艺」，属于「出门前的行李清点」 |

## 检查项（三档，跳过 ≠ 通过）

### 🔴 红线 —— 任一失败 = 不可发布（退出码 1）

| 编号 | 检查项 | 判据（怎么算通过） |
|---|---|---|
| **S1** | 密钥红线 · 工作区 | `check-secrets.js` 退出码 0（红线 0 条 / 无配置类文件混入 / `.env.example` 无真值）+ **未跟踪文件**用同一份规则表补扫 0 条 |
| **S2** | 密钥红线 · **全部 Git 历史** | 全部分支的**补丁体新增行**与**提交信息**扫一遍，红线规则 0 命中 |
| **S3** | 输入边界 | `check-boundaries.js` 退出码 0（数据库 CHECK ↔ 前端 JS ↔ 输入框 maxlength ↔ 接口层自检 四处数字一致） |
| **U1** | 公网可达 · 线上首页 | HTTP 200 + 页面含 `#board-list` + title 是站名 |
| **U2** | 公网资源齐全 | `/js/api.js`、`/js/data.js`、`/css/style.css` 均 200 且 > 500 B |
| **E1** | `.env` 忽略**真生效** | `git check-ignore -v .env` 有输出 —— 「.gitignore 里写了」和「规则真的生效」是两件事，这一条问 git 本人 |

### 🟡 提醒 —— 不阻塞发布，但发布前一定要知道

| 编号 | 检查项 | 判据 |
|---|---|---|
| **D1** | 工作区干净 | `git status --porcelain` 为空。**有未提交改动 ≠ 出错**，但要清楚：发布的是已提交并推送的那一版 |
| **D2** | 本地 HEAD 与远端 main 一致 | 两边同一个提交号。直连远端拿不到时退回本地 `origin/main` 并**注明「没直连」** |
| **D3** | 线上版本漂移 | 逐文件比 `HEAD:` 与线上同路径的哈希（换行已归一）。**落后不等于坏**，只说明「本地已有更新还没发」 |

### ⚪ 跳过 —— 跳过不等于通过

| 编号 | 检查项 | 什么时候跳过 |
|---|---|---|
| **W1** | 前端工艺门槛（frontend-rules / filter-check） | 默认不跑（要本地静态服务 + 浏览器渲染，单跑数分钟）。加 `--with-browser` 才跑；本地 8000 没服务也会跳过 |

## 怎么跑

```bash
# 默认：在项目根目录
node .workbuddy/skills/preflight-check/preflight-check.js

# 留下机器可读的报告
node .workbuddy/skills/preflight-check/preflight-check.js --json preflight.json

# 连前端工艺门槛一起跑（先把服务起起来）
python -m http.server 8000 --bind 127.0.0.1
node .workbuddy/skills/preflight-check/preflight-check.js --with-browser

# 在别的副本上跑（验证脚本自身、或想拿一份「另一个根目录」的结果）
node .../preflight-check.js --root <另一个项目根>

# 换了域名 / 想验网络这一层是真在查
node .../preflight-check.js --site <另一个线上地址>
```

退出码：红线全过 = `0`，任一红线失败 = `1`。参数写错 = `2`。

## 怎么证明它不虚报通过（反证，比「跑一次全绿」重要）

**一条只会报绿的检查等于没有检查。** 判断它是不是真在干活，要**故意弄坏一项**看它红不红 ——
而且每次只弄坏一处，看红的是不是**正好那一处**：

| 刻意弄坏什么 | 期望结果 | 说明 |
|---|---|---|
| 往某源码文件塞一行假的密钥字面量（**未提交**） | 只有 **S1** 红，并指出 `文件:行号` | 证明工作区扫描在干活 |
| 把假密钥提交进去，**再删掉并再提交** | **S1 绿、S2 红** | 只靠工作区扫描永远看不出这条；只有历史扫描能。这也是「删掉也没用、必须去平台作废密钥」的可执行证据 |
| 把接口层某个上限数字改得与数据库 CHECK 不一致 | 只有 **S3** 红，并列出「期望 X、实际 Y」 | 证明边界是当契约在验，不是摆设 |
| `--site` 指到一个没人听的地址 | **U1 / U2** 红 | 证明公网可达不是写死的一句「通过」 |

> 反证用的假密钥请写在**副本**里（`git clone` 一个靶场），别写进真仓库 ——
> 真仓库里出现任何像密钥的东西，哪怕明知是假的，也是自己给自己造的消防演习以外的事故。
>
> ⚠️ 靶场里若 `check-secrets.js` 还是**老版本**（末尾无条件 `main()`），本 Skill 不会被它带崩 ——
> 规则表是在**子进程**里取的（见文件顶部注释）。这条是实跑时踩出来的：本进程 `require` 旧版
> 会把整个检查进程一起 `process.exit(0)` 带走，报告打一半、退出码却是 0，属于最坏的那种假绿。

## 判据的边界（口径写清楚，免得后面自己骗自己）

- **S1 走的是「git 跟踪范围」**（`check-secrets.js` 的口径：与实际会被上传的内容严格一致）。
  未跟踪的新文件它看不见，所以本 Skill 用**同一份规则表**补扫了一层。
- **S2 排除 `check-secrets.js` 自己**：规则定义文件里必然写着各种密钥形态的样子，
  不排除就是稳定假阳性（第一轮实跑就是这么红的）。工作区扫描早就排除了它（`f !== SELF`）。
- **E1 只判「有没有被忽略」，不判「本机有没有 `.env`」**：本机有 `.env` 是正常开发配置，
  只要它提交不出去就不构成发布风险。把「文件不存在」当红线，会让每个开发者都卡在这一步。
- **D3 归一了换行与末尾空白**：本仓库 `core.autocrlf=true`，工作区是 CRLF、仓库里是 LF，
  不归一的话「完全相同的文件」也会被判成不同（第一轮实跑 11 个文件全报漂移，就是这个原因）。
- **W1 默认跳过**：数分钟的量级不适合塞进「出门前 10 秒的快检」。跳过时报告里会写明原因 ——
  跳过不是通过。

## 怎么加检查项

1. 在 `preflight-check.js` 里写一个 `checkXxx()`，返回 `{ id, title, level, summary, detail, note? }`，
   用 `add({...})` 收进 `checks`；
2. `level` 选 `blocker` / `warn` / `skip` —— 三档的打印分组与结论判定是自动的；
3. 在 `main()` 的调用序列里插进去；
4. 在**本文件**的检查项表里补一行（表是给人读的，代码是给机器跑的，两边都要）。
5. 若这一项属于某个已有门槛的地盘 —— **别在本文件里重写那条规则**，加一个「委托调用」就好。

## 已知边界（没做到的，写明白）

- **W1 默认不跑**：所以「前端工艺」这一层默认**没验过**，报告里是 SKIP 不是 PASS。
- **D3 只比「11 个可发布文件」**：不在名单里的文件（图片、文档、`data/*.json`）不参与漂移比对。
- **D2 直连远端需要凭据**：本机到 GitHub 走 SSH 密钥，需要时在环境里给
  `GIT_SSH_COMMAND`；拿不到就退回本地 `origin/main` 并注明「没直连」。
- **不检查数据库侧**：云端表结构、RLS 策略、频控触发器都不在这里验
  （那些由 `db/schema.sql` 与 MCP 通道单独核对）。这里只验「出门前的东西」。
- **不检查登录后的路径**：邮箱登录只在发布域名可用，匿名访问能覆盖的部分已覆盖。
- **不判「这个版本该不该发」**：它只回答「能不能发」。发什么内容是人决定的。

## 文件布局说明

本 Skill 的执行脚本放在**目录根**（`preflight-check.js`），与同目录的兄弟 Skill
（`frontend-rules/check-frontend.js`、`filter-check/filter-check.js`）保持一致 ——
仓库里的三个 Skill 排在一起时，路径形态一眼能对上。

## 输出与留痕

- 报告打到屏幕：按三档分组，每项一行 `[PASS|FAIL|WARN|SKIP] 编号 名称 — 摘要`，明细缩进在下面。
- `--json <路径>` 落一份机器可读结果（含每个检查项的原始明细），供留档 / 渲染成图。
- `run-log.md` 记**关键节点**（发布前一次、发布后一次），由人来写 ——
  **不自动追加**：发布前检查常在「改动还没提交」时跑，自动追加会让工作区一直脏着，
  反过来又让 D1 项永远报「未提交」，自己给自己添噪声。
