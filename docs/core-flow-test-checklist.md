# 核心流程测试清单 · 完整链路（CRUD 闭环）

> 用途：**一条可反复跑的回归线**。修 Bug 前跑一遍留档、修完再跑同一份，两份对比。
> 项目：热门时事真伪辨别网站（foxlings-project）｜站点 `https://rumor-check-12000.app.workbuddy.host/`
> 覆盖链路：**打开检查台 → 读取 plan_days/checkins → 写入 → 刷新确认 → 修改 → 删除**
>
> **读法**：每条用例四列 —— 步骤 / 期望 / **怎么算通过（可复现判据）** / 留什么证据。
> 判据必须是「别人照着做能得出同一个结论」的句子，不许写「看起来正常」。
>
> ⚠️ **两条纪律**（本项目一直用）：
> ① **一切以数据库 SELECT 的前后差为准，不以界面提示为准**（`api-contract.md` §6.4）；
> ② **断言必须真的会变红** —— 只证明「新的对」不够，要能证明「旧的在同一个输入上会错」
>   （负例靶子。Day 24 就是这么确认 20 条单测不是假绿的）。

## 一、先把范式名对上：`plan_days` / `checkins` 在本项目是哪两张表

课程链路里写的是打卡应用的**范式示例名**。本项目落在同一范式上，但记录流有两条：

| 课程说法 | 本项目实表 | 说人话 | 接口 |
|---|---|---|---|
| 打开**检查台** | `admin.html`（站方管理后台） | 登录 + 在 `admins` 名单里才进得去 | — |
| 读取 **plan_days**（主对象） | **`items`** 核查条目 | 编辑产出的核查结果，信源 JSONB 内嵌 | `api.getItems()` |
| 读取 **checkins**（时间累积记录） | **`reports`** 线索流 | 未登录也能提交，进 `pending` 队列 | `api.listAllReports()` |
| 读取 **checkins**（第二条记录流） | **`posts`** 论坛帖流 | 登录用户产生，走审核状态机 | `api.listAllPosts()` |
| 读取（Day 24 新增） | **`announcements`** 站方公告 | 后台口径含未公布草稿 | `api.listAllAnnouncements()` |
| 写入**打卡** | ①前台发帖 ②前台提交线索 ③**后台新建公告** | 见 C3 —— 注意后台唯一的「新建」入口只有公告 | — |
| **修改** | `posts` 审核状态机 / `announcements` / `profiles` | **`items` 刻意不可改**（热度不可篡改） | `api.setPostStatus()` 等 |
| **删除** | `posts` / `reports` / `items` / `announcements` | **真删、不可逆**（Day 24 撤掉回收站） | `api.deletePost()` 等 |

> 映射依据：`docs/cloud-data-service-v1.md` 第二节、`docs/day21-acceptance.md` §二·附。
> 「检查台」一词出自课程原文（本项目 Day 22 引过：「部署后**在检查台页面上**完成一次真实的修改和删除」）。

## 二、链路总览（跨页，别在一个页面里找全程）

```
       前台（index.html / mine.html）                后台（admin.html）
  ┌──────────────────────────────┐        ┌────────────────────────────────┐
  │ C3 写入：发帖 / 提交线索       │  ────▶ │ C2 读取：待审队列 / 线索收件箱   │
  │ （写入也在前台，不在后台）      │        │ C1 打开检查台（登录 + 管理员）   │
  └──────────────────────────────┘        │ C5 修改：审核通过 / 驳回 / 改公告 │
              ▲                            │ C6 删除：两击确认 → 真删         │
              │  C4 刷新确认（两边都要看）   └────────────────────────────────┘
```

**最容易踩的一条**：**后台没有「新建帖子 / 新建线索」的入口** —— 帖子与线索都在前台产生。
所谓「写入打卡 → 刷新确认」在本项目是**跨页**动作：前台写、后台看见。
后台能「新建」的只有**站方公告**（`#ann-form`）。

## 四、C2 · 读取（`plan_days` → `items`，`checkins` → `reports` / `posts`）

**判据的统一形态**：`#<区块>-count` 的条数 == `#<区块>-list` 的行数 == SQL 查出来的行数（三处一致）。

| # | 步骤 | 期望 | 怎么算通过（可复现判据） | 留什么证据 |
|---|---|---|---|---|
| C2.1 | 读条目（主对象） | 后台条目区列出全部条目 | `#items-count` 文案 = `共 N 条`，N == `SELECT count(*) FROM items`；`#items-list` 行数 == N | 截图 + SQL 结果 |
| C2.2 | 读线索（记录流①） | 后台线索收件箱列出全部线索 | `#reports-count` = `共 N 条`，N == `SELECT count(*) FROM reports` | 截图 + SQL |
| C2.3 | 读帖子（记录流②） | 后台读**全部**帖子（含待审 / 已拒），比前台宽 | `#posts-count` = `共 N 条`，N == `SELECT count(*) FROM posts`；前台公开列表只出 `approved`（**作者本人**额外看到自己那条 `pending`，`posts_read` 是 `status='approved' OR author_id=auth.uid()`） | 两页截图对照 + SQL |
| C2.4 | 读公告（后台口径） | 后台**含未公布草稿**，前台不含 | 后台 `#ann-count` = `共 N 条（已公布 M 条）`；前台轮播只有 M 条（`is_pinned = true`） | 两页截图 + SQL `count(*)` 与 `count(*) FILTER (WHERE is_pinned)` |
| C2.5 | 反向：公告草稿匿名**真的读不到** | 未登录 GET 拿不到 `is_pinned = false` 那行 | 匿名请求返回行数 == M（不含草稿）。**这条靠 RLS 的 `USING (is_pinned)`，不是前端过滤** | 探针输出（`verify/probe-day24-draft.js`） |
| C2.6 | 异常：读的时候断网 | 给**中文**提示 + 重试出口，页面不半渲染 | 顶部出现 `#admin-flash` 或 `renderLoadWarning` 的中文提示；控制台可 grep `[api]` 日志；**不出现**英文堆栈 | 截图 + 控制台 |

> ⚠️ **一个会骗人的坑（务必记住）**：首页榜单默认落在**「本周」**（`js/home.js` 的 `boardRange` 默认 `"week"`，
> 且**不写 localStorage**）。线上数据 `updated_at` 若已超 7 天，本周榜**天然 0 条**，
> 页面会显示「本周暂无新增核查，本月有 N 条 查看本月」。
> **不要据此判定「数据没读到」** —— 切到「本月」再看。这条已经让一个门槛卡死过一次。

## 五、C3 · 写入（记录一条）

| # | 步骤 | 期望 | 怎么算通过（可复现判据） | 留什么证据 |
|---|---|---|---|---|
| C3.1 | 前台发帖：登录 → 论坛 → 填标题/正文/分类/昵称 → 提交 | 一律落 `pending`，只有作者自己看得见 | 提交后**后台** `#pend-list` 多一行；`SELECT status FROM posts WHERE id = X` = `pending`；前台公开列表**看不到**它；`#compose-note` 给中文回执 | 前后各一张截图 + SQL |
| C3.2 | 后台新建公告：填标题/正文/勾「立即公布」→ 发布 | 公告落库，前台轮播立刻出现 | `SELECT count(*) FROM announcements` +1；`#ann-count` 的「已公布」数 +1；前台 `#notice-track` 出现该条 | 前后截图 + SQL |
| C3.3 | 同上但**不勾**「立即公布」 | 存为草稿，**前台看不到** | 库里 `is_pinned = false`；后台可见、前台轮播条数不变（见 C2.4/C2.5） | 截图 + SQL |
| C3.4 | 未登录提交线索：`mine.html` → `#rep-input` 填 5–500 字 → `#rep-add` | 落库，`author_id = 'anon'`；本机另留一份底 | 后台 `#reports-count` +1；`SELECT author_id FROM reports` = `anon`；**同时** `localStorage.fx_myreports` 多一条（本机留底，见 C4 的坑） | 截图 + SQL + localStorage 快照 |
| C3.5 | 写入后查「提交前 / 提交后」两次 SELECT | 行数 +1，且新行的必填字段都在 | 两次 `count(*)` 差 1；新行 `trim()` 后长度落在边界内（见 §九） | SQL 前后对照 |

**边界（写入侧，数字的口径）**：

| 字段 | 边界 | 真相在哪 |
|---|---|---|
| `reports.text` | 5–500 字 | 数据库 CHECK |
| `posts.title` | 4–60 字 | 数据库 CHECK |
| `posts.body` | 10–1000 字 | 数据库 CHECK |
| `posts.author_name` | 1–20 字 | 数据库 CHECK |
| `announcements.title` | 2–60 字 | 数据库 CHECK |
| `announcements.body` | 1–2000 字 | 数据库 CHECK |
| `announcements.sort_order` | -9999 – 9999 | 数据库 CHECK |

> 四处要对得上：**数据库 CHECK → 前端 JS → 输入框 `maxlength` → 接口层 `assertText`**。
> 门槛脚本 `check-boundaries.js` 就是查这四处的一致性（**锚点以数据库为准**）。
> 当前状态：PASS。

| C4.2 | 反向：不该出现的刷新后**也不出现** | `pending` 帖在公网论坛刷新后仍看不到 | 匿名/他人视角刷新前台论坛，列表里没有该 id | 截图 |
| C4.3 | 刷新后看数据来源 | 数据来自**云库**，不是本地兜底 | Network 里 `/.cloud/database/` 有请求、`data/data.json` **0 次**（Day 20 迁移纪律） | Network 面板截图 |
| C4.4 | 反向：清掉 localStorage 再刷新 | 云端内容**不受影响** | 清 `fx_*` 后刷新，C3.1 / C3.2 写的东西仍在（那是云库的）；**只有** C3.4 的「本机留底」会消失 | 前后截图 + localStorage 清空前后对比 |

> （因为匿名行 `author_id` 全是 `'anon'`，本人回读不到）。
> 于是 `mine.html` 的「我提交的待核查」刷新后**看起来还在** —— 但那可能是**本机留底**，
> **不是云库那条**。判据必须写清看的是哪一个（C4.4 就是对这一条的对照实验）。

## 七、C5 · 修改（PATCH）

| # | 步骤 | 期望 | 怎么算通过（可复现判据） | 留什么证据 |
|---|---|---|---|---|
| C5.1 | 后台待审区点「**通过**」 | `status: pending → approved`，文章立刻出现在公网论坛 | `api.setPostStatus()` 返回**改后的行**；控制台有 `[api] 审核帖子 X：status pending → approved`；SQL 前后对比 status 变了；发起前先 SELECT 确认 id 存在 | 截图 + 控制台 + SQL |
| C5.2 | 后台点「**驳回**」并填理由 | `status = rejected` + `reject_note` 落库 | SQL 读回 `reject_note` 非空且等于填的内容；作者侧看到驳回原因 | 截图 + SQL |
| C5.3 | 后台改公告（标题 / 正文 / 排序 / 是否公布） | 改后行回来；前台轮播顺序按 `sort_order` 变（大的在前） | `api.updateAnnouncement()` 返回值 == 提交的 patch；前台 `#notice-track` 顺序变化 | 前后截图 + SQL |
| C5.4 | 个人主页改昵称 / 签名 | 只改到**自己那一行** | SQL 读回该 `user_id` 行的新值；论坛里该作者的昵称跟着变；改完不能变成别人的（`WITH CHECK` 兜住） | 截图 + SQL |
| C5.5 | **反向：`items` 不可改** | 谁都改不了条目 —— 热度不可篡改 | 匿名 + **管理员**各发一次 `PATCH /items?id=…` 都拿 `401`（`permission denied for table items`）。`items` **没有任何 UPDATE 策略**，这是「数据库不可能」级 | 探针输出 |
| C5.6 | 异常：改一个**不存在**的 id | 明确中文错，**不是静默 204** | 抛「没有找到这条…（id=X）」+ `code = NOT_FOUND`；**不许**返回 200/204 假装成功 | 控制台 + 探针 |

> C5.6 是这条链路上最容易做错的地方：PostgREST 在不索要返回值时对改 0 行也回 `204` ——
> **静默失败比报错更难查**，所以 `api.js` 用 `fetchRowOrThrow()` 把存在性判断**前置**（`api-contract.md` §6.1）。

## 八、C6 · 删除（DELETE，真删）

| # | 步骤 | 期望 | 怎么算通过（可复现判据） | 留什么证据 |
|---|---|---|---|---|
| C6.1 | 后台点「删除」**一次** | 按钮变成「**确认？**」，**不执行** | 3 秒内没有网络请求；3 秒后按钮文本自动复原。`armDangerous()` | 截图（按钮文本）+ Network 面板 |
| C6.2 | 3 秒内**再点一次** | 真删，页顶给回执 | `#admin-flash` 出现「已删除《…》—— **真删，数据库里已经没有了**」；列表当场少一行 | 截图 |
| C6.3 | SQL 验证删除 | 行**真的没了** | `SELECT count(*) FROM posts WHERE id = X` == **0**。⚠️ **Day 24 起没有 `is_deleted` 这一列可查，那正是重点** | SQL 前后对照 |
| C6.4 | 公网视角验证 | 刷新后 GET 不再返回它 | 前台列表 + 匿名 GET 都不含该 id | 截图 + 探针 |
| C6.5 | 删条目 / 删线索 / 删公告 | 同 C6.1–C6.4 | 各自 `SELECT count(*)` == 0；回执文案含「真删」 | SQL + 截图 |
| C6.6 | 异常：只点一次就走开 | **什么都没发生** | 3 秒后按钮复原；SQL 里那行还在 | 截图 + SQL |
| C6.7 | 异常：非管理员调 `deletePost` | 被数据库拒，不是前端拒 | `401`（`posts_admin_delete` 没过）。**改前端解锁不了** | 探针输出 |
| C6.8 | 异常：删不存在的 id | 明确中文错 | 抛「没有找到这条…」+ `code = NOT_FOUND`；**不许假装成功** | 控制台 + 探针 |

> **「不可逆」放在哪**（Day 24 定稿）：按钮（两击确认）+ 文案（明写不可恢复）+ 回执（删完说一句）
> + 底稿（只有 `items` 有 `data/data.json` 可重灌，`posts` / `reports` 无副本）。
> 撤掉回收站之后，这道两击确认是**唯一的刹车**。

## 九、刁钻输入补充用例（找不到 Bug 时先跑这一节）

覆盖六类：**空值 / 超长 / 类型错 / 不存在 id / 越权 / 快速连点**。
每条都要求「拦截必须说人话」，不许静默兜底成 0、不许白屏。

| # | 输入 | 打哪里 | 期望 | 怎么算通过 |
|---|---|---|---|---|
| H1 | **空值**：标题/正文全留空直接提交 | 论坛发帖、后台发公告 | 前端拦 + 中文提示 | 提示元素（`#compose-note` / `#ann-note`）有中文；**不发请求**（Network 无 POST） |
| H2 | **纯空格**（`"     "`） | 同上 | 按空值拦（trim 后为 0） | 同上 |
| H3 | **超长**：标题 61 字 / 正文 1001 字 / 线索 501 字 | 三个输入框 | 输入框 `maxlength` 直接挡住 | 输入框里实际只有 60 / 1000 / 500 字 |
| H4 | **绕过页面**超长（接口层直投） | `api.createPost()` 等 | 接口层自检拦住 | 抛中文错；SQL 里没有落库新行（`assertText`） |
| H5 | **边界值**：正好 4 字标题 / 正好 3 字标题 | 论坛发帖 | 4 字过、3 字拦 | 数据库 CHECK `char_length(title) >= 4` 是真相 |
| H6 | **数字类输入非法值**（`sort_order` 填 `abc` / 空） | 后台公告排序权重 | 明确报错，**绝不静默兜底成 0** | 提示元素有中文错；SQL 里那行的 `sort_order` 保持不变 |
| H7 | **不存在的 id**：改/删一个假 id | `api.setPostStatus(99999)` / `deletePost(99999)` | 中文错 + `code = NOT_FOUND` | 同 C5.6 / C6.8 |
| H8 | **越权**：非管理员调管理接口 | 全部 `*_admin_*` | 数据库拒（401） | 探针：`verify/probe-day22-gate.js` 的闸门矩阵 |
| H9 | **快速连点**：提交按钮连点 5 次 | 发帖 / 提交线索 / 发公告 / 删除 | 只落**一条** / 只删**一次** | 按钮在第一次点击时同步 `disabled = true` + 文案变「提交中…」（`js/forum.js:322`、`js/admin.js` 各处）→ 后续点击无效；SQL 里只有 1 条新行 |
| H10 | **连点「删除」超过 3 秒** | 后台删除 | 第一次点 → 变「确认？」→ **超时复原** → 再点仍是「变确认」而不是直接删 | 反复点永不误删（这是防呆的设计意图，不是 bug） |

## 十、证据留档模板（前后各一份）

修复前 / 修复后**用同一份清单**，各交一份，两份并排看。

## 十一、我处理你报的 Bug 时走的顺序（固定四步）

你把问题按上面的格式发我，我按这个顺序回，**不跳步**：

| 步骤 | 我交什么 |
|---|---|
| **① 原因排序** | 列出**所有**可能原因并排序（最可能的在前），每条写「为什么可能是它」。**先不修** |
| **② 每个原因的验证方法** | 逐条给可执行的验证办法 + 谁会变红。**先证明不是它，再动下一个**（本项目 Day 24 就是这么排除掉 5 种其他可能的） |
| **③ 修复方案** | 锁定根因后给方案，并说明「为什么改这里而不是那里」「有没有带出新 Bug 的风险」（Day 24 修复时差点引入「下标错位」—— 滤掉坏元素后若用重新编号的 `i` 当删除下标，会静默删错条） |
| **④ 回归验证清单** | 本次改动**会碰到的**清单条目 + 定向单测 + 负例靶子（证明旧代码在同一输入上会红）。跑完交前后两份证据 |

**为什么先排序再验证**：直接跳到「我猜是 X」会**锚定**在第一个念头上，后面全在给它找理由。
排序 + 逐条排除，是唯一能把「我猜」变成「我证明」的路。
