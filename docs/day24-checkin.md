# Day 24 打卡：数据真实性自检（改 / 删 / 防呆 / 契约）

> 课程 Day 24 打卡的四项检测。四项一句话概括：
> **① 改的是真数据、② 删的是真删除、③ 不存在的 id 不装成功、④ 接口变了文档跟着变。**
>
> 验收口径照课程要求：**页面与数据库两端都看到才算数**，任何一端单独成立都不算。
> 检测日期：2026-10-10。

## 〇、落点选择：为什么拿「站方公告」这张表来验

课程模板说的是「把一条记录的**备注**改成测试-改」。本项目里字面叫「备注」的字段是
`profiles.note`（`api-contract.md` 第一节登记为「纯人读」），但它**没有后台编辑入口**，
不构成「在页面上改」的路径。

真正同时满足下面三条的是**站方公告**（Day 24 新交付的表）：

1. 后台有完整的**编辑 / 撤下 / 删除**入口（`admin.html` 的「⑤ 站方公告」区块）；
2. 它的正文是**自由文本**，改起来最接近模板里的「改备注」；
3. 它**一张表上同时有 PATCH 与 DELETE 两个接口**（`/api/announcements/:id`），
   正好把打卡四项一次验完，不用换表。

测试对象是脚本自建的两条记录，测完全部清除，**不碰任何真实内容**：

| id | 标题 | 用途 |
|---|---|---|
| 4 | `[打卡测试·修改] 待改的草稿记录` | ① 修改检测（`is_pinned=false` 草稿，前台不可见，不干扰访客） |
| 5 | `[打卡测试·删除] 待删的已公布记录` | ② 删除检测（`is_pinned=true`，好演示「GET 结果里消失」） |

## 一、① 修改检测 — 页面改的值，数据库里真的变了

**操作路径**：真实浏览器打开线上 `admin.html` → 登录管理员账号 → 点测试记录的「编辑」→
把正文改成 `测试-改` → 点「保存修改」→ **刷新整个页面** → 记录仍在且值为 `测试-改`。

**两端证据**：

| | 页面 | 数据库（`sql` 查询） |
|---|---|---|
| 改前 | `原始值：这是修改前的正文。` | `id=4  body = 原始值：这是修改前的正文。` `created_at = 22:24` |
| 改后 | `测试-改`（**刷新后重读仍是它**） | `id=4  body = 测试-改` `updated_at = 22:51:30` |

**为什么这条能证明「改的是库不是 DOM」**：刷新页面会让前端把整份数据从数据库重读一遍。
如果改动只留在前端内存/DOM 里，刷新就会退回原值。实际刷新后仍是 `测试-改`，
且库里的 `updated_at`（22:51:30）**晚于** `created_at`（22:24）—— 说明改的是库里那一行。

## 二、② 删除检测 — 两端都消失 = 真删

**操作路径**：在后台列表里点测试记录的「删除」→ 按钮变「确认删除？」→ 再点一次（两击确认）→
记录从列表消失。

**两端证据**：

| | 页面 | 数据库 |
|---|---|---|
| 删前 | 后台列表 **4 行**，含 `[打卡测试·删除]` | `SELECT count(*) FROM announcements WHERE id=5` → **1** |
| 删后 | 后台列表 **3 行**，该条已不在 | `SELECT count(*) FROM announcements WHERE id=5` → **0** |

Day 24 起没有回收站（站方决定「不留堆着没用的数据」），所以这里**不是打个标记**，
是行本身没了。这跟 Day 22 的形态正好相反：那时删完行还在、挂着「已回收」，
用户看不出发生了什么；现在行直接消失，本身就是最好的回执。

## 三、③ 防呆检测 — 不存在的 id 不许装成功

**检测目标**：把 id 换成不存在的 `99999` 调 PATCH / DELETE，必须给出**明确的中文错误**，
且**页面不崩、接口不返回 500 裸报错**。

这一项**分两层测**，因为两层要防的不是同一件事：

| 层 | 测法 | 结果 |
|---|---|---|
| 接口层（页面上下文，管理员身份） | `api.updateAnnouncement(99999,…)` / `api.deleteAnnouncement(99999)` | `没有找到这条公告（id=99999）—— 它可能已经被删掉了；如果它本该还在，请确认你的账号有没有相应权限。` `code=NOT_FOUND` |
| 裸通道（绕过接口层，直接打数据库 HTTP 口） | `PATCH/DELETE /.cloud/database/rest/announcements?id=eq.99999` | `HTTP 401` + `permission denied for table announcements` —— **不是 500** |

**额外做了一遍匿名身份的对照**：未登录时同样的操作会被 `42501` 先拦住，
页面给出的是「这条操作没有被允许……」的中文提示，**同样不崩、同样不是 500**。
两层的文案不同是对的：匿名确实没有权限，而管理员有权限、只是这条记录不存在 ——
错误原因不同，说法就该不同。

**页面未捕获 JS 异常：0 条。** 「删一个不存在的数据还报成功」的情况没有出现。

## 四、④ 契约同步检测 — 接口变了，文档跟着变

`api-contract.md` 第三节能看到 PATCH / DELETE，且标记「已实现」：

```
/api/posts/:id            PATCH / DELETE    ✅ 已实现   （Day 22 接 · Day 24 把 DELETE 改成真删）
/api/announcements/:id    PATCH / DELETE    ✅ 已实现   （Day 24）
/api/items/:id            DELETE            ✅ 已实现
/api/reports/:id          DELETE            ✅ 已实现
```

**顺带修掉一个契约自身的不同步**：这一节的标题原来叫「**预留接口**（接后端时按此实现，不提前写）」，
但表格里早已全是「已接」—— 标题与内容对不上，Day 28 验收时看标题会被误导。
本轮改成「**接口实现状态（计划 → 实际）**」，写明状态列的读法，并把全表的
`✅ 已接` 统一成 `✅ 已实现`，让「文档说实现了」和「代码里找得到」能一眼对上。

契约全文：`api-contract.md`（仓库内）；在线地址见提交说明。

**为什么这三项必须登录才能验**：本站身份只有「邮箱验证码 / 密码」一条路（Day 20 起记着），
验证码只有本人邮箱能收 —— 这是整个打卡里唯一没法自动化的环节。做法是弹出一个**真实浏览器窗口**
（与访客同一条链路），由站方登录一次，脚本每 2 秒探一次登录态，确认「已登录**且**在 `admins` 名单里」
之后自动跑完三项并截图。

> 首轮脚本里写错了一处：`auth` 是 `const` 声明，**不会挂到 `window` 上**，
> 而检测写的是 `window.auth` —— 于是无论登没登录都被判成「没登录」，脚本一直空等（站方反馈「一直卡着」）。
> 改用 `typeof auth !== "undefined"` 后修复，并先用无副作用的 headless 验证过才让站方重新登录一次。

## 六、边界与如实记（不美化）

1. **① 的「刷新仍在」主要靠数据库读数举证**：页面侧留下的是刷新前的截图（`checkin-02-after.png`），
   刷新后的整页截图因为页面滚回顶部、可能没框住公告区，所以没有作为主证。
   真正的硬证据是那行数据本身 —— 刷新后前端重读库、读到的就是 `测试-改`，
   而库里 `updated_at` 也确实变了。
2. **② 的「GET 结果里消失」是在后台管理口径上验的**（`listAllAnnouncements()`）。
   前台口径（`listAnnouncements()`）只出 `is_pinned=true` 的，测试记录删掉后自然也不在前台 ——
   对删掉的记录来说两种口径结论一致，但**测的是同一个事实的两个侧面**，不该混为一谈。
3. **公告没有乐观锁**：两人同时编辑同一条会互相覆盖。当前只有站方一人用后台，接受。
4. 本轮的改动（`api-contract.md` 第三节）需要重新发布才会体现在线上站点；
   但契约是仓库文件，不影响页面运行。
