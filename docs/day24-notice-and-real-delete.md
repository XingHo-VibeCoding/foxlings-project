## 一、撤回软删除：删了什么、改了什么

Day 22 的做法是「删除 = 打标记，数据留在库里，随时能捞」。跑了一轮之后站方的判断变了：
**数据堆着没用，删除就该是不可逆的。** 于是整套撤除。

### 1.1 云库（DDL，已落线上库）

| 动作 | 对象 |
|---|---|
| DROP | 三个 `BEFORE DELETE` 触发器（items / posts / reports） |
| DROP | 函数 `soft_delete_rows()`、`restore_item(text)`、`restore_report(bigint)` |
| DROP | 读策略 `items_admin_read`（当初为「后台看得见回收站」而开） |
| 重建 | `items_read_all`（`USING (true)`）、`posts_read`、`reports_read_own` —— 都去掉 `NOT is_deleted` |
| 重建 | `bump_item_view()` —— 去掉 `AND NOT is_deleted`（浏览计数不再需要跳过已回收条目） |
| DROP COLUMN | `items.is_deleted` / `posts.is_deleted` / `reports.is_deleted` |

> 顺序很关键：**先删掉所有引用 `is_deleted` 的对象（触发器 → 函数 → 策略 → 视图/函数体），最后才 DROP COLUMN**。
> 顺序反了会直接报依赖错误。

### 1.2 接口层（`js/api.js`）

- `getItems()` / `getPosts()` 去掉 `.eq("is_deleted", false)` —— 没有「展示口径 / 管理口径」之分了，
  读到的就是全部、也是唯一的一份。
- **删除三兄弟改用 `.delete().select()`**：
  一次请求同时完成「删掉」和「拿到删掉的那一行」；拿不到返回行就抛中文错
  （id 不存在，或账号没权限 —— 两种可能都点到）。
  Day 22 不能这么写（触发器取消了物理删除，被取消的行不进 `RETURNING`），撤掉软删后这条限制自然消失。
- 删掉 `restorePost` / `restoreItem` / `restoreReport` / `callRestoreRpc` / `describeRestoreError` / `listAllItems`。
- 新增 `notFoundError(label, id)`：把「这条不在」的说法收成一个函数，改/删两条路共用。
- `fetchRowOrThrow` 保留 —— PATCH 那条路仍然需要「写之前先确认这条在」，
  而且它拿到的整行就是「改动前的快照」。

### 1.3 管理端（`admin.html` / `js/admin.js`）

- 三个列表摘掉「已回收」徽标、计数里的「（其中已回收 N 条）」、以及「恢复」按钮；
  删除后仍然**整体重载**（行当场消失，本身就是最好的回执）。
- 新增 **操作回执**（`.admin-flash`，`role="status"`）：删完在页顶明说一句
  「已删除《…》—— 真删，数据库里已经没有了」，7 秒后自己淡出。
- `armDangerous(btn, confirmText)` 支持自定义确认文案，删除按钮第二次点击显示「确认删除？」。
- 三个删除区块的说明都加了一句「删除是**不可恢复**的」—— 不留侥幸心理。
- 新增「站方公告」区块（见下）。
- 顺手把事件绑定收进 `bind(id, ev, fn)` 壳里：元素缺失时报错到控制台，而不是静默什么都不做
  （Day 22 的教训：脚本与 HTML 对不上时，表现出来就是「点了没反应」，最难查）。

### 1.4 为什么撤（一句话版）

软删除的收益是「兜住管理员手滑」，代价是**一个状态位要渗透进每一条读路径**
（读策略 ×3、`api.getXxx()` ×2、后台列表 ×3），漏一处就是「删了还读得到」这种没有信号的坏。
而手滑这一半已经有更便宜、更直接的防线：按钮上的两击确认 + 明说不可逆。
收益与代价不成比例 → 撤。完整权衡记在 `api-contract.md` 第七节。

## 二、站方公告栏

### 2.1 数据：新表 `announcements`

| 字段 | 说明 |
|---|---|
| `title` | 2–60 字 |
| `body` | 1–2000 字，**换行原样显示**（规则一条一行） |
| `is_pinned` | **是否公布**。`false` = 先写好放着，前台看不到 |
| `sort_order` | 排序权重，大的在前；同权重时新的在前 |
| `author_id` | 发布人（种子行 `'seed'`），不参与权限判断 |

**为什么不复用 `posts`**：两边说话的人不同（公告只有站方能发）、生命周期不同（公告长期挂着）、
展示位置不同（顶栏 vs 列表）。硬塞进 `posts`，论坛列表 / 审核队列 / 前端筛选每一处都要多一个
「这条是公告不算帖子」的判断，漏一处公告就混进帖子流。

**RLS 两条策略**：

- `announcements_read_all`：`FOR SELECT TO anon, authenticated USING (is_pinned)`
  —— 公开读，但**只出已公布的**。「先写好、暂不公布」的稿子匿名真的读不到，靠策略不靠前端。
- `announcements_admin_write`：`FOR ALL TO authenticated USING/WITH CHECK (在 admins 名单里)`
  —— 一条覆盖增 / 改 / 删。

> ⚠️ 两条读策略（公开读 + 管理读）是 **OR** 关系：管理员会话下光靠 RLS 会把未公布的稿子也带出来，
> 所以展示口径**必须在前端再写一次**（`api.listAnnouncements()` 带 `.eq("is_pinned", true)`）。
> 这和 Day 22 在 items 上踩的是同一个坑，这次一开始就避开了。

### 2.2 接口：五个方法

| 方法 | 用途 |
|---|---|
| `api.listAnnouncements()` | **展示口径**：只出已公布的，按权重降序 |
| `api.listAllAnnouncements()` | **后台口径**：含未公布的稿子 |
| `api.createAnnouncement({title, body, sortOrder, isPinned})` | 发布 |
| `api.updateAnnouncement(id, patch)` | 改（标题 / 正文 / 排序 / 是否公布） |
| `api.deleteAnnouncement(id)` | 删（真删） |

### 2.3 论坛页：轮播公告栏

位置在论坛视图标题之下、发帖区之上 —— 进论坛第一眼就看见。

轮播的几条分寸（都在 `js/forum.js`）：

- **只有一条时不转**，也不显示切换控件（没得切，控件只会碍眼）；
- 多条时自动转（6 秒一条），但**鼠标停进来 / 键盘焦点落进来就暂停** —— 正在读的那条不该被抢走；
- **用户自己切过之后重新计时**（刚点完立刻又被自动跳走，是最烦人的那种）；
- 系统里开了「减少动效」（`prefers-reduced-motion`）就不自动转 —— 手动切换照常能用；
- 切到别的标签页时暂停，回来接着转；
- 自动轮播**不播报**给屏幕阅读器（每隔几秒打断一次根本没法用），
  只有用户主动切换才往 `#notice-live` 写一句；
- 视窗高度按当前那条同步（`syncNoticeHeight`），公告长短不一也不留一大块空白；
- 一条公告都没有时**整块收起**，不留空框；公告读失败也只收起，不把论坛拖成错误态。

底部那块「发帖前先看：社区规则与审核」**按站方要求保留**：公告栏是站方口径的通知与提醒，
那儿是发帖细则的完整版。

### 2.4 后台：发布入口

管理后台新增「站方公告」区块：表单（标题 / 正文 / 是否立即公布 / 排序权重）+
列表（每条可编辑、可「撤下 / 公布它」、可删除）。

- 「撤下 / 公布」是**可逆**操作，不设两击确认（确认只留给不可逆的那一步）；
- 「删除」是**不可逆**的，两击确认；
- 「编辑」把内容读回表单，按钮变「保存修改」，另给一个「取消编辑」。

**社区规则从此是数据不是代码** —— 站方在后台改一句话，全站立即生效，不用改前端、不用重新发版。

## 四、遗留与取舍（如实记）

1. **撤销自身的边界**：`is_deleted` 列一旦 DROP，**Day 22 那批「已回收」的行也一并没了**。
   实际执行前先查过三张表的 `is_deleted=true` 计数，都是 0 —— 所以这次撤销**没有丢任何数据**。
   如果当时有，就必须先决定「捞回来还是扔掉」再动手。
2. **公告的 `is_pinned=false` 只挡住了「读」**：稿子对匿名/普通登录用户不可见，
   但管理员在后台看得到（这是设计目的）。边界在「管理员可信」这个前提上。
3. **公告没有乐观锁**：两个人同时编辑同一条公告，后保存的会覆盖先保存的。
   当前只有站方一个人用，接受；多人共管时再补 `updated_at` 比对。
4. **`admin.html` 的公告区截图是「强制显示」的版式预览**（未登录态下把 `#admin-body` 显出来），
   不是真实管理员会话 —— 真实数据下的样子要登录后看。
5. **匿名提交频控仍未做**（Day 22 起就挂在账上）：RLS 只管「谁」，不管「多快」。
   唯一真空白，方案见 `docs/day22-crud-loop.md` §12.8③，阈值需要站方拍板。
6. **本轮改动尚未发布** —— 线上还是 Day 23 的版本，等站方看过公告文案再发。
