# Day 28 · 结营复盘：28 天里我最大的一个认知改变

> 项目：热门时事真伪辨别（证据整理员，不是审判官）
> 站点：https://rumor-check-12000.app.workbuddy.host/　｜　2026-10-18

## 最大的认知改变：**「做完了」不算数，「能被当场验证」才算数**

28 天前，我对"完成"的定义是：功能写出来了、我这边点过一遍、没报错。今天我对"完成"的定义是：

> **任何人、不问我一句话、照着一条写死的命令或 URL，能亲眼看到同一个结果。**

区别不在于多写了多少测试，而在于**证据换了主人**——从"我说是"变成"它自己说"。

### 这个改变在项目里留下的三个实例

**① 判据要写死，感觉要靠边。**
第 25 天做 preflight-check 时，我第一次被自己教的：一条检查如果不写清"什么算过"，那它就不是检查，是心情。后来 D3（线上版本漂移）的判据精确到「逐字节比对 11 个资产、且必须用不 trim 的 `gitBlob()`」——因为用会 trim 的读法，11 个文件会**全部误报**。判据错一点，结论就整体作废。

**② 反向验证：证明"是它修好的"，而不是"它出现时问题恰好在消失"。**
第 27 天修 SDK 兜底，正向证据只有一半（有兜底 15 张卡）。补了反向：摘掉兜底重跑同一探针 → 0 张卡 → 问题回来了。**只有正反都成立，因果链才算闭合。** 这条已经写进 Day 28 的修复提示词模板，成为硬要求。

**③ 假绿比失败更危险，所以要让失败响亮。**
最警醒的一次是验证工具本身出假绿：探针数容器子元素，把 loading 占位节点数成了结果——"站内命中 0 条"被判成通过。还有 `process.exit()` 把检查进程带走、报告打一半退出码却是 0。从那以后我记住：**失败要大声，静默的"通过"要先怀疑工具自己。** `verify/probe-live-core-flow.js` 现在遇到页面自报加载失败会直接退出 2、拒绝出"看起来正常"的图。

### 前后对比

| | 28 天前 | 今天 |
|---|---|---|
| "完成"= | 功能在我这跑通了 | 陌生人照命令重跑，结果一致 |
| 出错时 | 看报错、改代码 | 先怀疑工具与判据，再改代码 |

| 删除/发布 | 顺手就做 | 有手册、有锚点、有演练耗时（回退 109s/123s，恢复 40s/34s） |

## 次要的两个改变

1. **安全是"让权限在数据库那层长死"，不是"前端记得拦"。** items 没有 UPDATE 策略 = 热度物理上不可篡改；写探针的期望就是"被拒"。前端校验只是早提示，不是防线。
2. **内容缺口是缺口，代码解决不了就是解决不了。** 23 条全是【示例】、9 天没更新——这件事 28 天里我一直没修，因为它不是 bug。承认"这块帮不上"比用代码做样子诚实。

## 如果重来一遍，我会改的三件事

1. **第 1 天就建 `docs/` 判据习惯**——前两周的"我试过没问题"全都留不下证据，后期补证据花了成倍时间。
2. **内容灌装别排在最后**——代码再稳，首页全是【示例】也撑不起"辟谣榜"三个字。项目最大的缺口至今是内容，不是技术。
3. **演练尽早**——回滚是第 26 天才第一次真做的。如果第 10 天就演练过，第 26 天发现的手册问题（备份目录写仓库内会被公开）就不用拖那么久。

## 留给未来维护者的三句话

1. 改判据前先跑一遍现状——**你比的不是我，是上一版判据**。
2. 云端改结构必须同步 `db/schema.sql`，改数字要同时动四处（数据库→前端 JS→输入框→接口层）。
3. 一切验收的底线只有四条：公网能开、网关在线、一次写入、刷新后还在。其余都是从这四条长出来的。
