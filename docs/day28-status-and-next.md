## 三、后续优化计划（课程到结营为止，以下是结营后自己迭代的方向）

### ① 接一个真实数据源（对应附录 F）

- 现状：内容靠人工整理，`data/data.json` 只是种子源头，23 条全是示例。
- 做法：抓权威辟谣来源（如中国互联网联合辟谣平台、各地官方通报）→ 落 `items` 表。
- 卡点：`items` **没有任何客户端写策略**（实测 `PATCH /items` → 401），灌内容必须走 SECURITY DEFINER 函数或管理员通道；建函数后**必须 `REVOKE` 再 `GRANT`**（托管库会自动授 EXECUTE 给 anon）。
- 优先级：**最高**——这是产品最大的缺口，且只有内容能让它成立。

### ② 加注册登录（对应附录 D）

- 现状：`js/auth.js` 已有身份层，匿名可用；但注册流程、登录后的体验（头像、昵称、"我的线索"跟随账号）没打磨。
- 为什么值得做：**未登录提交的线索只存本机**，换设备就丢；登录后线索才存云端并能被读回——这条链路现在只差"用户愿意注册"。
- 优先级：高（决定核心操作是否真的留得下来）。

### ③ 给核心记录加统计页（复用现有 GET 接口 + 前端图表）

- 核心记录 = `items`。「完成率」的语义 = 已核查 / 已戳穿占比（`verdict` 四档 + `cross_check` 三档）。
- 动手路径（**独立验收官只看文档给出的路径**，说明架构足够清楚）：
  1. **表**：前端现算就不用动 `db/schema.sql`；要服务端聚合就照 `bump_item_view()` 新增函数 + `REVOKE/GRANT`。
  2. **接口**：`js/api.js`（唯一接口层）加 `getItemStats()`，页面不许直连 `.from(` / `rpc(`。
  3. **前端**：现成位点已经在了 —— 容器 `index.html` 的 `#board-stats`，渲染函数 `js/home.js` 的 `renderStats()`，加第三张卡即可；错误态跟着 `DATA_STATE` 走，不用另写。
  4. **契约**：`api-contract.md` 同步一行。
  5. **门槛**：`check-secrets` + `check-boundaries` → `preflight-check --with-browser` → 发布后 `check-live-version.js main`。
- 优先级：中（锦上添花，改动最小，适合当"继续改"的第一练手）。
