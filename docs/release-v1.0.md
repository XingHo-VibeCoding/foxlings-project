## 六、备份方式（代码标记 + 数据导出）

### 6.1 代码版本标记

```bash
git tag -a v1.0.0 <sha> -m "..."          # 或 -F <文件>（中文信息走文件更稳）
git push origin refs/tags/v1.0.0
git ls-remote origin 'refs/tags/*'        # 直连核实 —— 本地有 tag ≠ 远端有
```
**判据**：远端能列出来才算数。只在本机的 tag，出事那天拿不到。

### 6.2 数据导出（发布前做）

```bash
node db/export-data.js --out <备份目录> --label v1.0.0
```
- ⚠️ **备份目录必须放在仓库之外**（脚本会直接拒绝写在仓库内）。本项目发布上传整个目录，备份放进去 = 备份被公开。
- 产物：每张表一个 `.json` + `manifest.json`（记录提交号、时刻、以及每张表导出的**覆盖程度**）。

**本次实测（2026-10-15 22:44）**：

| 表 | 结果 | 覆盖程度 |
|---|---|---|
| `items` | 23 行 / 库里 23 | ✅ full |
| `posts` | 7 行 / 库里 7 | ✅ full |
| `announcements` | 2 行 / 库里 2 | ✅ full |
| `reports` | HTTP 401 | ❌ denied（匿名读不到） |
| `profiles` / `admins` | 200 + 0 行 | ❓ unknown —— **不能判成「空表」**：RLS 挡光时同样是 200 + 空数组 |

> 这就是本项目备份的**能力边界**：匿名身份只能备 `items` / `posts` / `announcements` 三张表。用户资料、管理员、举报记录的误删，**这份备份救不回来** —— 要它们得走管理员通道，是已知缺口。

### 6.3 恢复路径（已实测可执行）

```bash
node db/restore-from-backup.js --dir <备份目录>    # 生成 restore.sql（INSERT + ON CONFLICT DO NOTHING）
# 然后把语句**一条一条**送进云数据库执行（数据通道一次只收一条）
```
- identity 主键（`posts` / `announcements` / `reports` 的 `id` 是 `GENERATED ALWAYS AS IDENTITY`）必须加 `OVERRIDING SYSTEM VALUE`，否则实测直接回 **428C9**；恢复后还要 `setval` 把序列推到 `MAX(id)`，否则下次正常插入会撞主键。
- 脚本会读 `db/schema.sql` 自己判断哪张表是 identity，避免「脚本里的死名单」和「真结构」两处漂移。
- **实测（2026-10-15 22:46）**：`announcements` 那条恢复语句真跑成功（返回 `[]` = `DO NOTHING` 空操作）、`setval` 返回 `2`；跑完三张表行数仍是 23/7/2，**零污染**。

### 6.4 备份纪律

1. **含表结构变更的发布，必须先导出数据** —— 结构变了再导，导出来的就已经是坏的那份。
2. **备份不做校验 = 没有备份**：恢复语句必须真跑过一次（本次就是这么验的）。
3. 备份 ≠ 回滚。回滚退的是**代码**，备份救的是**数据**，两条路分开练。
