## 六、备份方式（代码标记 + 数据导出）

### 6.0 三秒回答「上一版是哪一版、怎么取回」

> 检测口径：能**当场**指出版本标记在哪，并说清怎么取回 —— 说不出，备份就只是念头不是资产。

```bash
# ① 版本标记在哪：本地 + 远端各查一次（本地有 ≠ 远端有）
git tag -l -n1                                    # 本地
git ls-remote origin 'refs/tags/*'                # 远端（直连核实）

# ② 上一版是哪一版：
git tag -l v0.9.0 -n1                             # → v0.9.0 = d94034a（v1.0 之前的线上版）

# ③ 怎么取回（把线上退回那一版）：
git fetch --tags origin && git checkout --force v0.9.0
node tools/check-live-version.js v0.9.0            # 逐字节核验是否真的退回去了
```

| 资产 | 在哪 | 指向 / 判据 |
|---|---|---|
| 版本标记 | git tag（本地 + 远端） | `v1.0.0`→`f3d9f0d`（当前线上）；`v0.9.0`→`d94034a`（上一版） |
| 数据备份 | 工作区 `verify/backups/20261015-224454-v1.0.0/`（**不在仓库内**，因为发布公开整个仓库目录） | `manifest.json` 记提交号 + 导出时刻 + 每张表覆盖程度 |
| 云端快照 | 平台侧托管库自身 | 本项目**没有**独立快照能力，只有上面这份导出；`reports`/`profiles`/`admins` 备不到（见 6.2） |

**一句话**：「上一版是 **v0.9.0 = d94034a**，取回方法 = `git fetch --tags` → `checkout --force v0.9.0` → 同目录重新发布 → `tools/check-live-version.js v0.9.0` 核验。」

### 6.1 代码版本标记

```bash
git tag -a v1.0.0 <sha> -m "..."          # 或 -F <文件>（中文信息走文件更稳）
git push origin refs/tags/v1.0.0
git ls-remote origin 'refs/tags/*'        # 直连核实 —— 本地有 tag ≠ 远端有
```
**判据**：远端能列出来才算数。只在本机的 tag，出事那天拿不到。

### 6.2 数据导出（发布前做）

```bash
node db/export-data.js --out <备份目录> --label v1.0.0
```
- ⚠️ **备份目录必须放在仓库之外**（脚本会直接拒绝写在仓库内）。本项目发布上传整个目录，备份放进去 = 备份被公开。
- 产物：每张表一个 `.json` + `manifest.json`（记录提交号、时刻、以及每张表导出的**覆盖程度**）。

**本次实测（2026-10-15 22:44）**：

| 表 | 结果 | 覆盖程度 |
|---|---|---|
| `items` | 23 行 / 库里 23 | ✅ full |
| `posts` | 7 行 / 库里 7 | ✅ full |
| `announcements` | 2 行 / 库里 2 | ✅ full |
| `reports` | HTTP 401 | ❌ denied（匿名读不到） |
| `profiles` / `admins` | 200 + 0 行 | ❓ unknown —— **不能判成「空表」**：RLS 挡光时同样是 200 + 空数组 |

> 这就是本项目备份的**能力边界**：匿名身份只能备 `items` / `posts` / `announcements` 三张表。用户资料、管理员、举报记录的误删，**这份备份救不回来** —— 要它们得走管理员通道，是已知缺口。

### 6.3 恢复路径（已实测可执行）

```bash
node db/restore-from-backup.js --dir <备份目录>    # 生成 restore.sql（INSERT + ON CONFLICT DO NOTHING）
# 然后把语句**一条一条**送进云数据库执行（数据通道一次只收一条）
```
- identity 主键（`posts` / `announcements` / `reports` 的 `id` 是 `GENERATED ALWAYS AS IDENTITY`）必须加 `OVERRIDING SYSTEM VALUE`，否则实测直接回 **428C9**；恢复后还要 `setval` 把序列推到 `MAX(id)`，否则下次正常插入会撞主键。
- 脚本会读 `db/schema.sql` 自己判断哪张表是 identity，避免「脚本里的死名单」和「真结构」两处漂移。
- **实测（2026-10-15 22:46）**：`announcements` 那条恢复语句真跑成功（返回 `[]` = `DO NOTHING` 空操作）、`setval` 返回 `2`；跑完三张表行数仍是 23/7/2，**零污染**。

### 6.4 备份纪律

1. **含表结构变更的发布，必须先导出数据** —— 结构变了再导，导出来的就已经是坏的那份。
2. **备份不做校验 = 没有备份**：恢复语句必须真跑过一次（本次就是这么验的）。
3. 备份 ≠ 回滚。回滚退的是**代码**，备份救的是**数据**，两条路分开练。

### 8.3 ⚠️ 走查中撞到的一条真实风险：页面硬依赖 `cdn.jsdelivr.net`

**现象**：23:0x 走查时，线上首页**自报「加载失败」**，五步一步都走不了。不是代码坏了 —— 是 4 个页面都直接用
`<script src="https://cdn.jsdelivr.net/npm/@tencent-ai/workbuddy-cloud-sdk@dev/lib/index.global.js">`，
而这个域名**此刻从本机不通**，拿不到 `window.WorkBuddyCloud`，页面就只能报加载失败。

**镜像探测（`verify/probe-cdn-mirrors.js`，同一文件同一路径）**：

| 端点 | 结果 |
|---|---|
| `cdn.jsdelivr.net` | ❌ fetch failed |
| **`fastly.jsdelivr.net`** | ✅ **200 · 71931 B · 769 ms** |
| `gcore.jsdelivr.net` | ❌ fetch failed |
| `testingcf.jsdelivr.net` | ❌ fetch failed |
| `unpkg.com` | ✅ 200 · 71931 B · 1196 ms |

**判断**：这是**外部依赖的单点**（不是本次发布引入的回归 —— 22:01/22:04 那两张取证图就是没有顶替、真链路截成功的，属于间歇性不通）。
但后果很重：**CDN 一抽风，整站对访客就是不可用**，而且页面看不出是"网络的锅"。

**建议（待定，未擅自改代码）**：给 4 个页面的 SDK 引入加**同源多端点兜底**（`cdn.jsdelivr.net` → `fastly.jsdelivr.net` → `unpkg.com`），彻底解掉单点。这属于代码改动 + 需要重新发布 + 重跑 D3，**等你点头再动**。
