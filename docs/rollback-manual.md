# 回滚手册 · 时事真伪辨别

> 建立于 Day 26（2026-10-15）。同日完成一次**真实回退演练**，全程耗时记录在 §五。
> 结论先说：**静态托管没有"一键回滚"按钮，唯一的回退动作就是"把旧快照重新部署上去"** —— 本手册写的就是这条路，且已实测走通。

| 锚点 | 指向 | 是什么 |
|---|---|---|
| tag `v1.0.0` | `f3d9f0d` | 首个正式发布版（含首屏自动回落），**已推远端** |
| tag `v0.9.0` | `d94034a` | v1.0 之前的线上版（含 safeIndex 三修复、无回落），**已推远端** |

- 核验"线上到底是哪一版"不靠肉眼：`node verify/check-live-version.js <tag>`（工作区副本），把线上 11 个资产与 `git show <tag>:<file>` 逐一 sha256 比对，全等才判"线上 = 那一版"。
- 判据不依赖浏览器和 CDN，CDN 抽风时照样能用（这次演练期间 CDN 断了，核验照常工作）。

## 二、静态托管回退路径（已演练 ✅）

发布通道没有历史版本回退参数，`directory` 决定目标应用。所以回退 = **把工作区物化成旧版内容，再对同一目录执行一次发布**（同一应用、同一链接）。

```bash
# ① 物化旧版（--force 只覆盖被追踪文件，未追踪文件如 .env 不受影响）
git checkout --force v0.9.0

# ② 发布（用平时发布同一动作；分享链接不变）
#    —— 目录不变 → 平台自动命中原应用，覆盖线上内容

# ③ 核验线上真的退回去了（退出码 0 = 11/11 一致）
node <工作区>/verify/check-live-version.js v0.9.0

# ④ 演练/修复结束后，仓库回主线（工作区与 HEAD 恢复一致）
git checkout --force main
```

**三条纪律**（这次演练验证过的）：
1. 回滚前 `git status` 必须是干净的 —— 回滚动作会覆盖工作区，脏东西会先被 `--force` 冲掉。
2. 回滚的是**部署**，不是仓库历史：**不要**为了回滚去 revert/重写 main；仓库停在 v1.0.0，线上临时跑旧版，修好后重新发布即可。
3. 回滚结束必须跑一次步骤 ④ + 重新发布，并留下"恢复后线上 = v1.0.0"的核验输出。

**实测耗时（2026-10-15）**：回退全程 **109 秒**（物化 → 部署 → 逐字节核验通过）；恢复全程 **40 秒**。→ 意味着"线上出事 → 退回上一版可用"的止损窗口在 **2 分钟以内**。

**这次演练顺带暴露的一件事**：回滚会把新版才有的体验一起丢掉 —— 退到 v0.9.0 后，首屏自动回落消失，访客第一眼看到的又是空周榜。**回滚是可用性止损，不是体验保全**；按下回滚按钮前，先想清楚这一版相对上一版多修了什么。

## 三、【判断表】什么情况必须回滚，什么情况不回滚

| # | 情况 | 动作 | 理由 |
|---|---|---|---|
| 1 | 线上**白屏 / 核心流程跑不通**（榜读不出、详情打不开、论坛发不了），且当场热修 5 分钟内没把握 | **必须回滚** | 首页不可用 = 站点不可用，止损优先；2 分钟就能退回可用版 |
| 2 | **安全问题**：密钥泄漏到线上、越权可写、注入面暴露 | **立即回滚 + 撤换密钥** | 泄漏面每多一分钟就多一分钟风险；回滚先止血，密钥另行走 `.env` → 换 key → 重发 |
| 3 | 新版把**老用户数据搞坏**（误删字段、写坏 localStorage 结构） | **必须回滚** | 继续跑会让更多用户被写坏；退回旧版先停止伤害 |
| 4 | **数据层故障**（RLS 配错、表被删、函数失效） | **回滚前端没用，禁止拿它当解法** | 前端退一万遍，数据库还是坏的。走 §四 的数据层恢复路径 |
| 5 | **误删数据** | 回滚无效，走数据恢复（§四） | 删除是真删（Day 24 拍板），代码回滚不还原数据 |
| 6 | 纯**文案错别字、样式小瑕疵、非关键交互小 Bug** | **不回滚，热修** | 回滚的代价是丢掉新版全部修复（见 §二末尾）；瑕疵不值得 |
| 7 | **CDN / 第三方依赖挂了**导致页面加载失败 | **不回滚** | 旧版依赖同一个 CDN，退了也一样挂；等恢复或换源 |
| 8 | 新版**功能正常但效果不好**（排序不满意、文案风格不喜欢） | 不回滚，改了再发 | 这不是事故，是迭代；回滚解决不了"想得不对" |

**一句话口径：可逆的、丢数据/丢可用性的 → 回滚；不可逆的数据问题 → 走恢复；观感问题 → 热修。**

## 四、云函数回退 / 数据恢复（只备查，Day 26 未实操）

> 本项目没有自建 HTTP 服务层，"云函数"侧 = 托管数据库里的 **2 个函数（`bump_item_view` / `enforce_report_rate_limit`）+ 1 个触发器 + 17 条 RLS**。它们的"回退"含义如下。

**云函数 / 数据库结构回退（备查）**：
- 数据通道拦 DDL → 结构变更必须走 MCP `exec_sql`，**一次只收一条**；改之前先把当前定义 SELECT 出来存档（`pg_get_functiondef` / `pg_get_viewdef`），否则退无可退。
- 回退 = 用存档的定义**重放**（`CREATE OR REPLACE FUNCTION`）；托管库给新建函数自动授 EXECUTE 给 anon，重放后必须补 `REVOKE ALL ON FUNCTION f(args) FROM PUBLIC, anon;` 再 GRANT。
- 改完必须同步 `db/schema.sql`，并跑 `verify-project`（H4 写探针期望就是"被拒"）。
- ⚠️ 频控**必须是触发器**（RLS 策略里 `EXISTS(SELECT…)` 对 INSERT 恒空 = 静默失效），"回退"到策略写法等于关掉频控，不许。

**数据恢复（备查）**：
- 托管库无时点恢复（PITR）保证；`items` 没有任何 UPDATE 策略 = 热度不可篡改，但**删除是真删、不可逆**（Day 24 拍板撤软删除，勿回退）。
- 恢复手段只有两条：① 从最近的导出/种子（`data/data.json`）重灌，② 让用户重新提交。**所以删之前的两击确认 + 明写不可恢复，是唯一真的在防线的机制。**
- 真要恢复时先断源头：别让前端继续写，先 RLS 收紧（`exec_sql` 一条 `ALTER TABLE ... DISABLE` 或临时策略），再谈灌数据。
