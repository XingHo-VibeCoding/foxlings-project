# 回滚手册 · 时事真伪辨别

> 建立于 Day 26（2026-10-15），同日完成**两次真实回退演练**（第二次带数据完整性校验）。
> 一句话口径：**回滚只解决代码问题；数据被误删，回滚救不回来，只能靠发布前导出的备份重新导入。**
> 所以本手册分三层写，且三层是三个独立动作 —— 「代码回退」和「数据恢复」要分开练，别指望一个动作解决两件事。

---

## 〇、出事了先做这三件事

1. **判断是哪一层坏了**（对照 §一 判断表）—— 判错层 = 白折腾，还耽误时间。
2. **止损优先**：代码问题就退代码（实测 **2 分钟内**能退回上一版可用状态）；数据问题先别让前端继续写。
3. **留证据再动手**：回滚会覆盖现场，**现场只有一次**。动手前先把这两样存下来：
   ```bash
   git status --short                                        # 现场有哪些未提交改动
   node tools/check-data-counts.js --tag 回滚前 --out 回滚前快照.json   # 数据基线
   ```
   ⚠️ **第二条不是可选项**：没有「回滚前快照」，§三 的「数据层核验」就没有参照物，只能靠嘴说没坏。
   ⚠️ **第一条也不是走过场**：`--force` 会**直接丢弃**未提交的改动且不可恢复（本手册作者走查时就亲手丢过一次）。有未提交改动 → 先 `git stash` 或先提交，再动手。

## 一、触发条件：什么情况必须回滚

| # | 情况 | 动作 | 理由 |
|---|---|---|---|
| 1 | 线上**白屏 / 核心流程跑不通**（榜读不出、详情打不开、论坛发不了），且当场热修 5 分钟内没把握 | **必须回滚代码** | 首页不可用 = 站点不可用；退版本 2 分钟搞定，热修没把握就别赌 |
| 2 | **安全问题**：密钥泄漏到线上、越权可写、注入面暴露 | **立即回滚 + 撤换密钥** | 泄漏面每多待一分钟就多一分钟风险；回滚先止血，换 key 另走 `.env` → 重发 |
| 3 | 新版把**用户数据写坏**（写坏 localStorage 结构、写坏字段） | **必须回滚代码** | 继续跑会让更多用户被写坏；退回旧版先停止伤害（已写入的坏数据不一定能修，见第三层） |
| 4 | **数据层故障**：RLS 配错、函数/触发器失效、表被删 | **回滚前端没用，禁止拿它当解法** | 前端退一万遍数据库还是坏的。走 **第二层**（云函数回退），必要时 + 第三层 |
| 5 | **数据被误删** | 回滚无效，走 **第三层** | 删除是真删、不可逆；代码回滚不还原数据 |
| 6 | 纯**文案错别字、样式小瑕疵、非关键交互小 Bug** | **不回滚，热修** | 回滚的代价是丢掉新版全部修复（见 §二·第一层末）；瑕疵不值得 |
| 7 | **CDN / 第三方依赖挂了**导致页面加载失败 | **不回滚** | 旧版依赖同一个 CDN，退了照样挂；等恢复或换源 |
| 8 | 新版**功能正常但效果不好**（排序不满意、文案风格不喜欢） | 不回滚，改了再发 | 这不是事故，是迭代 |

**一句话：可逆的、丢可用性/丢数据的 → 回滚；不可逆的数据问题 → 走恢复；观感问题 → 热修。**

## 二、三层回退

### 分层对照

| 层 | 解决什么 | 动作 | 本项目对应物 | 演练状态 |
|---|---|---|---|---|
| **第一层 · 代码回退** | 前端代码问题 | 静态托管**重新部署上一版快照** | `workbuddy_sites_deploy`（目录决定应用） | ✅ **已实操演练 2 次**（记录见 `docs/rollback-drill-record.md`） |
| **第二层 · 云函数回退** | 数据库侧逻辑问题 | **重新部署上一版代码**（函数/触发器/策略定义） | `db/schema.sql` 里的函数与 RLS 定义 | 📖 **手册内容，不实操** |
| **第三层 · 数据恢复** | 数据被误删/写坏 | 用**发布前导出的备份重新导入** | `db/export-data.js` → `db/restore-from-backup.js` | 📖 **手册内容，不实操**（仅恢复 SQL 的**生成 + 单条零污染实跑**验过，全量恢复未实操） |

> **两层为什么不实操 —— 各一句原因**：
> - **第二层**：本次发布的代码差异只有 `js/home.js` 一个文件，**不含任何表结构 / 函数 / 策略变更**，没有「上一版数据库定义」可退；为演练而凭空重放一遍云函数，等于在没有故障时主动改线上数据库，风险大于收获。
> - **第三层**：本项目当前**数据完好无损**，要实操「数据恢复」就得先真的删掉真实数据再导回来 —— 拿真实内容赌演练，代价不可接受。所以只验到「备份能导出 + 恢复语句能生成 + 真跑过一次零污染」，**完整删除→恢复闭环留到 Day 27 用数据副本练**。

### 第一层 · 代码回退（静态托管回退上一版）✅ 已实操演练

**关键事实：静态托管没有「一键回滚」按钮。** 发布通道只有「部署」和「下线」两个动作，`directory` 决定发到哪个应用。所以回退 = **把工作区物化成旧版内容，再对同一目录发布一次**（同一应用、同一链接）。

```bash
# 0. 前置两件事（都不是可选项）
git fetch --tags origin                  # ① 让 tag 就位 —— 新克隆/浅克隆常缺 tag，缺了第 1 步会报
                                         #    "pathspec 'v0.9.0' did not match"
git status --short                       # ② 必须为空 —— --force 会丢弃未提交改动且不可恢复
                                         #    有改动 → 先 git stash 或先提交，再往下走

# 1. 物化旧版（--force 只覆盖被追踪的文件；未追踪文件如 .env 不受影响）
git checkout --force v0.9.0

# 2. 发布（平时发布同一个动作；目录不变 → 命中同一应用 → 线上被旧版覆盖）
#    入口：平台「设置 → 数据管理 → 应用」（没有一键回滚，回滚就是"拿旧内容再发一次"）

# 3. 核验线上真的退回去了（退出码 0 = 11/11 逐字节一致）
node tools/check-live-version.js v0.9.0  # ⚠️ 部署刚返回时可能 ENOTFOUND（DNS 未落定）→ 隔几秒重试

# 4. 核验数据没被碰（拿 §〇 存下的「回滚前快照」当参照物）
node tools/check-data-counts.js --tag 回退后 --compare 回滚前快照.json

# 5. 故障排除后：仓库回主线，重新发布
git checkout --force main
# 再发布一次，然后按 §三 走一遍验证
```

**三条纪律**：
1. 回滚的是**部署**，不是仓库历史 —— **不要**为了回滚去 `revert` / 重写 main。仓库停在最新提交，线上临时跑旧版。
2. 结束后必须走步骤 4，并留下「恢复后线上 = 最新版」的核验输出。
3. 回滚前先想清楚**这一版相对上一版多修了什么** —— 退回旧版会把这些一起丢掉。本次演练就实测到了这点：退到 v0.9.0 后，首屏自动回落消失，访客第一眼看到的又是空周榜。**回滚是可用性止损，不是体验保全。**

**实测耗时**：回退全程 **123 秒**（22:47:58 → 22:50:01，含一次域名解析失败后的重试等待）；链路正常时约 **30 秒**（物化 1 秒 + 部署 23 秒 + 核验数秒）。恢复 **34 秒**。→ **止损窗口在 2 分钟以内。**

### 第二层 · 云函数回退（重新部署上一版代码）📖 手册内容，不实操

本项目的「云函数」= 托管数据库里的 **2 个函数 + 1 个触发器 + 17 条 RLS 策略**（没有自建 HTTP 服务层）。它们的「重新部署上一版」= **用上一版定义重放**。

```sql
-- 步骤 1：先把**当前**定义存档（没有存档就没有"上一版"可退）
SELECT pg_get_functiondef('enforce_report_rate_limit'::regproc);
SELECT pg_get_functiondef('bump_item_view'::regproc);
SELECT * FROM pg_policies WHERE schemaname='public';      -- 策略存档
```

```bash
# 步骤 2：拿到上一版定义（db/schema.sql 是版本的真相来源）
git show v0.9.0:db/schema.sql
```

```
# 步骤 3：逐条重放（数据通道拦 DDL/多语句 → 走云数据库执行通道，一次一条）
CREATE OR REPLACE FUNCTION ... ;
```

**四个必须知道的坑**：
1. **是 `CREATE OR REPLACE`，不是删了重建** —— 删函数会连带删掉依赖它的触发器。
2. **托管库给新建函数自动授 EXECUTE 给 anon** → 每次重放后必须补
   `REVOKE ALL ON FUNCTION f(args) FROM PUBLIC, anon;` 再按需 `GRANT`。漏了这一步 = 函数对匿名可调。
3. **频控必须是触发器，不能回退成 RLS 策略** —— 策略里 `EXISTS(SELECT …)` 对 anon 的 INSERT 恒空，是**静默失效**（看着有策略，其实没在管）。回退到策略写法等于关掉频控。
4. **改完必须同步 `db/schema.sql`**，否则下次「上一版定义」就是从错的源头取的。

**回滚后必须验**：跑 `verify-project` —— `H4 写接口` 那一项就是专门查权限边界的（4 发探针期望「被拒且零污染」），`H2` 查表在不在。

**为什么不实操（一句原因）**：本次发布**不含表结构/函数变更**，没有「上一版数据库定义」可退；硬造一次第二层演练等于在没有故障时主动改线上数据库，风险大于收益。
→ 下次真改结构时，**改之前先跑 `export-data.js`**（第三层前置），再按本层步骤执行并留下实操记录。

### 第三层 · 数据恢复（备份重新导入）📖 手册内容，不实操

> **前提：备份必须是发布前做的。** 发布含表结构变更时，**先导出数据再改结构** —— 结构变完再导，导出的已经是坏的那份。

```bash
# ① 发布前：导出（备份目录必须在仓库之外！本项目发布会公开整个项目目录）
node db/export-data.js --out <仓库外目录> --label v1.0.0

# ② 出事时：把备份还原成可执行的 SQL
node db/restore-from-backup.js --dir <备份目录>
# 产出 restore.sql：INSERT ... ON CONFLICT (id) DO NOTHING（只生成 INSERT，不生成 UPDATE/DELETE）

# ③ 逐条送进云数据库执行通道（一次只收一条）
# ④ 复查：
#    · 行数与 manifest 里的 dbCount 一致（用 content-range，不是"取回多少行"）
#    · 三张表指纹与备份时一致（tools/check-data-counts.js）
```

**已经踩过并写进脚本的坑**：
- `posts` / `announcements` / `reports` 的 `id` 是 `GENERATED ALWAYS AS IDENTITY` —— 显式插 id **实测直接回 428C9**，必须写 `OVERRIDING SYSTEM VALUE`；恢复后还要 `setval(..., MAX(id))`，否则下次正常插入撞主键。生成脚本会读 `db/schema.sql` 自己判断，不让「脚本里的死名单」和真结构两处漂移。
- 一律 `ON CONFLICT (id) DO NOTHING`：重复执行不产生重复行，也**不会覆盖现场已有的数据**。
- 恢复工具**只有 INSERT 能力** —— 不给它「顺手改一下」的余地。

**实测（2026-10-15 22:46）**：`announcements` 那条恢复语句真跑成功（返回 `[]` = `DO NOTHING` 空操作），`setval` 返回 `2`；跑完三张表行数仍是 23 / 7 / 2，**零污染**。

**为什么不实操（一句原因）**：本项目当前数据完好，要实操「数据恢复」必须**先真删掉真实数据再导回来** —— 拿真实内容赌演练，代价不可接受。
→ 因此本层只验到「**备份能导出 + 恢复语句能生成 + 真跑过一次零污染**」；完整的「删除 → 恢复」闭环留到 Day 27 用数据副本做。

**⛔ 必须说清的边界 —— 这份备份救不了什么**：

| 表 | 备份覆盖 | 后果 |
|---|---|---|
| `items` / `posts` / `announcements` | ✅ 全量 | 误删可恢复 |
| `reports` | ❌ 读不到（401） | **举报记录误删不可恢复** |
| `profiles` / `admins` | ❓ 无法判定（200 + 空数组 ≠ 空表，RLS 挡光也是这个样） | **用户资料 / 管理员列表误删不可恢复** |

→ 要覆盖这三张表，需要管理员通道的备份方案。**这是已知缺口，不许假装没有。**
→ 在缺口补上之前，`profiles` / `admins` 的操作纪律是：**只增不删**；删除类操作必须两击确认 + 明写不可恢复（Day 24 已定的规矩）。

## 三、回滚后的验证方法（四层，缺一层都不算验完）

| 层 | 命令 / 动作 | 怎么算通过 |
|---|---|---|
| **1 字节层** | `node tools/check-live-version.js <tag 或提交号>` | **11/11 逐字节一致**，退出码 0。不依赖浏览器与 CDN，链路抽风时也能用 |
| **2 语义层** | 同上命令末尾那行 | 「线上 js/home.js 含 `autoFallbackRange` = true/false」与目标版本一致 |
| **3 数据层** | `node tools/check-data-counts.js --compare <回滚前快照>` | 三张表行数（`content-range` 的库里总数）与指纹**全部一致** →「回滚没碰数据」 |
| **4 页面层** | 浏览器真开一次线上首页 | 页面渲染出来、能交互、控制台 0 报错。（CDN 抽风时会自报「加载失败」→ 这是环境问题不是回滚失败，别混判） |

> ⚠️ **数据层为什么必须单独验**：代码回滚和数据是否完整**没有因果关系** —— 但人出事时容易想当然「我退了版本所以没事了」。把指纹比出来，才叫查过。
> ⚠️ 指纹**排除 `views` 列**：访客点进详情页会让它涨，那是真实业务写入，算进指纹就是自己制造假警报。
