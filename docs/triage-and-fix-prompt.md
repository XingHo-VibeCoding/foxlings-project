# 拿到试用记录之后：选卡点 → 写提示词 → 给复验任务

> 配套：`docs/trial-record-template.md`（记录表）· `docs/trial-kit-outsider.md`（任务脚本）
> 用法：把记录表底下「四、卡点清单」那几行（K1/K2/K3…）贴进来，按本文 §1 排序选一个最高优先级，按 §2 套成提示词交给 AI/自己，按 §3 生成最小复验任务发回给试用者。

## §1 先排序：哪一条是最高优先级

### 1.1 两个维度打分（各 0–2 分，相加）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| **X 断在哪** | 只影响这一步之后的无关步骤 | 这一步能绕过去，后面还能做完 | **核心链路断在这，后面全做不下去** |
| **Y 错的代价** | 只是慢一点、丑一点 | 让人困惑，但不会做错事 | **让人形成错误认知，且界面不会报错**（自以为存住了/删掉了，其实没有） |

**核心链路** = 打开 → 看到核心数据 → 完成一次核心操作 → 刷新确认 → 修改 → 删除（本项目的核心操作 = 提交一条待核查线索）。

### 1.2 优先级判定

| 总分 | 级别 | 处置 |
|---|---|---|
| **4** | **P0** | 立刻修。陌生人根本用不了，或会带着错误认知离开且无人提醒 |
| 3 | **P1** | 本轮修 |
| 2 | **P2** | 排进下轮，写进 `docs/expectation-gap.md` |
| 0–1 | **P3** | 记下，不排期（主观吐槽、审美） |

### 1.3 两条优先于打分的硬规则

1. **同一条卡点多人复现 > 单人偶发。** 两个试用者都卡在同一步，哪怕只有 2 分，也按 P1 处理。
2. **`E 做完了但理解错了` 一律不低于 P1。** 这类没有报错、没有红字，用户以为成了——是唯一一种"界面全绿但产品说谎"的失败，也是最容易被判成"能用"而漏掉的。
   > 例：第 5 步「改一改」。本项目的线索**没有编辑功能**，试用者很可能会"删掉再发一条"然后告诉你"改好了"。他不报错、你也不报错，但功能确实不存在。

### 1.4 排序工作表（照抄填）

| # | 现象（原话） | 类型 | X 断在哪 | Y 代价 | 总分 | 级别 | 是否多人复现 |
|---|---|---|---|---|---|---|---|
| K1 | | | | | | | □ |
| K2 | | | | | | | □ |
| K3 | | | | | | | □ |

**→ 最高优先级卡点：K____（级别 __）**

## §2 修复提示词模板（套好直接发）

> 结构沿用 Day 24 定的口径：**只给现象/证据、复现步骤、报错原文、已尝试动作；原因排序 → 验证方法 → 修复方案 → 回归清单。**
> 前半段不许写"我觉得是 xx 的锅"，后半段才允许推测。

```text
【现象】
<试用者原话，一字不改>·发生在第 __ 步（<步骤名>）。

【证据】
· 试用编号 T-__，时间 2026-__-__ __:__，设备 <安卓/苹果 + 浏览器>，网络 <Wi-Fi/流量>
· 截图：<文件名>
· 页面自报：<页面上的提示文字，抄原文；没有就写"无任何提示">
· 控制台报错：<原文；没有就写"无">

【复现步骤】
1. 手机浏览器打开 https://rumor-check-12000.app.workbuddy.host/
2. <点什么>
3. <点什么>
4. 实际结果：<…> ｜ 预期结果：<…>

【已尝试的动作】
· <自己试过什么、结果如何；没试过就写"未尝试">

【原因排序（按可能性从高到低，每条附上一条"怎么验证它"）】
1. <原因 A> —— 验证：<一条能当场判真假的检查/命令/探针>
2. <原因 B> —— 验证：<…>
3. <原因 C> —— 验证：<…>

【修复方案】
· 先验证上面第 1 条。只有验证成立才动手改；不成立就顺位往下。
· 改哪里：<文件 + 位置>；改法：<一句话>
· 不改哪些（防止顺手扩大改动范围）：<…>

【回归清单】（每条都要能判过/不过）
· [ ] <同一台手机、同一步骤重走一遍，现象消失>
· [ ] <相邻步骤没被带坏：___>
· [ ] 线上资产核验：node tools/check-live-version.js <提交号>  → 11/11
· [ ] 数据行数未变：node tools/check-data-counts.js --tag after --out b.json --compare <回滚前快照>
· [ ] <该卡点专属的反向验证：把修复摘掉，现象必须回来>
```

### 2.1 填写时的三条纪律

1. **【原因排序】必须给验证方法。** 只写原因不给验证 = 猜；猜对了也没法复用到下次。
2. **必须有一条反向验证。** 摘掉修复，现象要能回来——否则你无法证明是这个改动修好的（Day 27 的 SDK 兜底就是这么验的：有兜底 15 张卡 / 摘掉 0 张卡）。
3. **报错原文照抄，含英文。** 界面给用户看中文，英文原文留给 console 和提示词。

## §3 修复后给试用者的最小复验任务

> 要求：**只走修复的那一步，不重跑整条链路**；**≤ 2 分钟**；**只说点什么，不说原理**；**不许提示答案**。
> 发出去之前，自己先在手机上走一遍确认能过（走不通说明没修好，别发给用户）。

```text
谢谢你上次提的那一条，我改了一下。
能不能帮我花 2 分钟再试一次？还是用手机浏览器打开：

https://rumor-check-12000.app.workbuddy.host/

1. <点什么>
2. <点什么>
3. <点什么>

然后告诉我：这次 <具体动作> 成了吗？
成了 / 没成 / 跟上次一样 —— 回一个字就行。
如果还是不行，麻烦把屏幕上那句话抄给我。
```

**复验判据**（写进回归清单，不是发给用户）：

| 判据 | 过 | 不过 |
|---|---|---|
| 用户回复 | 「成了」且能说出他做了什么 | 「跟上次一样」/ 抄回来的是报错原文 |
| 我自己复走 | 同一步骤现象消失 | 现象仍在 |
| 相邻步骤 | 没被带坏 | 出现新问题 → 回滚（见 `docs/rollback-manual.md`） |

## §4 样例（Day 27 那条卡点，照着套的成品，供对照格式）

> 现象：陌生人手机打开首页，**一列卡片都没有**，底部写着「数据未就绪」。
> 类型：D（白屏/报错）｜X=2（后面全做不下去）｜Y=2（文案还让用户以为是自己网络不好）→ **P0**
> 原因排序：① 4 个页面硬引 `cdn.jsdelivr.net` 且无兜底 —— 验证：换 `fastly.jsdelivr.net` 直连是否 200；② 文案甩锅 —— 验证：grep 错误文案是否出现"你的网络"。
> 修复：SDK 改 cdn→fastly→unpkg 三来源兜底 + 四处文案不再归咎用户网络（`5edc0b5`）。
> 反向验证：摘掉兜底调用点重跑同一探针 → 卡片数 15 → 0。
> 复验任务（发给用户的三句话）：「再用手机打开这个网址 → 首页是不是有一列卡片了？→ 回我一句『有了』或『还是空的』。」
